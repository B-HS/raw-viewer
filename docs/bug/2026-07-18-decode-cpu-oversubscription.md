# 탐색 중 CPU 99% 지속·팬 폭주 — 디코드 워커 × OpenMP 초과구독

## 증상
CR2 153장 폴더(실사진)를 탐색하면 M5 Max(논리 18코어)에서 CPU가 99%로 지속되고 팬이 돌며, 프리로드 범위 밖 사진 클릭 시 "Decoding" 표시가 수 초 이상 지속. v0.5.1 실사용 검증에서 보고.

## 원인 (조사 워크플로 3관점, 파일:라인 근거는 당시 세션 기록)
1. **초과구독**: 디코드 워커 수 계약(논리코어-1 = 17)이 "디코드는 단일 스레드" 전제였는데, build.rs가 `LIBRAW_FORCE_OPENMP`로 LibRaw 내부 병렬화를 켜면서 워커당 OMP 팀(기본 = 전체 코어 18)이 생성 — 최악 17×18 ≈ 306 스레드가 18코어에서 경합 + libomp 기본 200ms 스핀대기. 두 결정이 서로 모순이었다.
2. **버려지는 풀디코드 연쇄**: 기본 L2Policy::Idle이 150ms 유휴마다 현재 사진의 22MP AHD 풀디코드(L2)를 큐잉하는데, L2는 디스크 캐시 미대상 + 1.5GB 스토어에서 곧 축출 → 훑기 중 사진마다 낭비 실행. 취소는 LibRaw 단계 경계에서만 확인되어 실행 중 중단 불가.
3. **워커 포화로 현재 사진 기아**: 이웃 L1 투기 프리로드(근접 4장)와 스테일 고우선 잡이 워커를 점유해, 먼 사진 클릭 시 새 L0/L1이 heap 선두인데도 실행할 워커가 없음. 프리로드 범위(radius 3) 밖 사진은 L0조차 사전 생성되지 않아 콜드 스타트.

## 해결 (v0.5.2, 커밋 c552f2a)
- main.rs에서 `OMP_NUM_THREADS=4`·`KMP_BLOCKTIME=0` 캡(미설정 시에만) — 불변식: heavy 동시성 × 팀 크기 ≈ 코어 수.
- 워커 레인 분리: light(L0 전용) 2개 + heavy(L1/L2) `(logical/4).clamp(2,4)`개, 큐도 2개.
- 이웃 L1 투기 프리로드 제거(neighbor_jobs — L0만).
- 전방 L0 전체 선로딩: `preload_l0` 커맨드 + L0 세대 플래그(navigate의 cancel_outside에 죽지 않음, 새 preload가 이전 세대 일괄 무효화). 프론트는 스캔 완료·이동 디바운스(800ms) 시 전방 미로딩분 최대 500장 요청.
- IDLE_DELAY 150→400ms, 큐에 남은 스테일 L2(비현재)는 실행 직전 스킵, f16 변환 루프에 주기적 취소 체크.
- 재방문 플래시: 프론트 stale best 가드에 `renderer.hasImage` 결합 — 텍스처 없으면 L0 먼저 표시 후 L1 스왑.

## 검증
같은 폴더 실기동: 전방 65장 L0 자동 프리로드, 패닉 0, t+40s/60s **유휴 CPU 0.0%**. cargo test 324 통과.

## 교훈
- 스레드 풀 위에서 도는 라이브러리가 자체 병렬화를 갖는지(OpenMP 등)를 반드시 확인하고, **동시성 × 내부 팀 크기** 불변식을 명시하라. 워커 수 계약을 바꾸는 결정(OpenMP 활성화)은 그 계약 지점(worker_count)도 함께 갱신해야 한다.
- 유휴 트리거로 무거운 작업을 발사할 때는 "결과가 보존되는가(캐시), 취소되는가"를 함께 설계하지 않으면 훑기 패턴에서 전부 낭비가 된다.
